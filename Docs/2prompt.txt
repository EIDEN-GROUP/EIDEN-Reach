# PART 2 — WHAT THE EMAIL SEQUENCE SYSTEM MUST BE

The sequence system should be a complete email automation engine, not simply a bulk email sender.

It must allow users to construct multi-step workflows, enroll selected contacts, send personalized emails, wait for specific periods or events, detect replies, branch workflows and automatically stop or continue based on defined conditions.

Think of it as an automation engine for each individual contact.

Every enrolled contact must have its own independently tracked execution state.

## 1. Main sequence interface

Create or complete the Sequences module with these sections:

**Sequences overview**

Display:

- Total sequences.
- Active sequences.
- Draft sequences.
- Paused sequences.
- Completed sequences.
- Total active enrollments.
- Emails scheduled.
- Emails accepted by the provider.
- Replies received.
- Positive replies.
- Bounces and unsubscribes.
- Meetings generated where actual booking data exists.

Include search, status filters, owner filters, sorting and pagination.

Each sequence should have:

- Name and description.
- Created by and owner.
- Created and updated dates.
- Current status.
- Number of enrolled contacts.
- Number of completed enrollments.
- Email sending activity.
- Reply and conversion statistics.

Do not display invented statistics.

Build a structured sequence creation flow.

### Step 1 — Basic information

- Optional associated pipeline or sales objective.

## 2. Example sequence

Create the following as a demonstration of expected sequence behavior.

**B2B prospect outreach**

<step>Initial email</step>

Day 0: Send a personalized introduction.

Wait three business days.

<step>Check for reply</step>

If a human reply is received:

- Stop future automated emails.
- Mark enrollment as Replied.
- Update the CRM activity timeline.
- Notify the assigned salesperson.
- Create a follow-up task.

If no reply arrives:

Continue to follow-up email.

Day 3: Send a short follow-up in the existing conversation thread.

Wait three business days.

If no reply:

Day 6: Send a value-focused email with a relevant resource or proposition.

Wait four business days.

If still unanswered:

Day 10: Send a final polite follow-up.

Then mark the enrollment Completed.

This is an example sequence, not a fixed workflow. Every delay, branch and email must be editable.

# PART 4 — THE EXECUTION ENGINE

This is the backend foundation that makes sequences actually work.

Do not implement the sequence engine as frontend timers or browser-side JavaScript.

## 1. Individual contact execution

Every enrollment must maintain an independent state machine.

Implement meaningful states such as:

- Pending.
- Active.
- Waiting.
- Scheduled.
- Sending.
- Paused.
- Replied.
- Completed.
- Bounced.
- Unsubscribed.
- Suppressed.
- Cancelled.
- Failed.
- Needs Review.

Store the current step, enrollment status, next scheduled execution, sequence version, contact, mailbox and execution history.

Maintain separate execution states for individual steps.

Never infer the state of all enrollments only from the parent sequence status.

## 2. Persistent scheduling

Every scheduled step must have a durable database record.

At minimum, store:

- Enrollment ID.
- Sequence version.
- Step ID.
- Scheduled execution time in UTC.
- Recipient time zone.
- Current status.
- Attempt count.
- Last attempt.
- Next retry.
- Idempotency key.
- Last error code and safe error details.
- Completion timestamp.

The database is the source of truth.

Cloudflare Queues are execution triggers, not the sole storage for pending jobs.

If the queue loses or expires a message, the system must be able to identify and recover the due job from the database.

Implement periodic reconciliation to find:

- Overdue scheduled jobs.
- Stuck processing jobs.
- Expired locks.
- Failed jobs requiring review.
- Jobs missing their expected queue message.
- Incomplete sends requiring reconciliation.

## 3. Concurrency and idempotency

This is mandatory.

The system must prevent:

- Two workers sending the same step simultaneously.
- Duplicate enrollment.
- A sequence executing a completed step again.
- A message being resent after an uncertain provider response without reconciliation.
- Two CRM events being created for one inbound message.

Use database transactions, conditional updates, leases or locking mechanisms and unique constraints.

Do not promise true exactly-once SMTP delivery. SMTP does not offer a universal idempotency guarantee.

Instead, design reliable duplicate prevention, message reconciliation and explicit states for ambiguous delivery outcomes.

An SMTP timeout after the server has accepted a message must not cause blind retries.

## 4. Sequence versioning

When a sequence is edited:

- Preserve the original version for existing enrollments where necessary.
- Make changes to future enrollments explicit.
- Allow administrators to create a new version.
- Define whether active enrollments migrate to a new version.
- Never silently change a contact's scheduled steps.

Record who changed the sequence and when.

# PART 5 — CUSTOM MAILBOX AND EMAIL INTEGRATION

The platform uses custom-domain mailboxes provided by Hostinger or compatible email providers.

There is no Google Workspace dependency.

The application must provide its own mailbox interface.

## 1. Provider-independent adapter

Inspect the current provider architecture and reuse it.

The provider integration layer should support, where available:

- Connection verification.
- IMAP authentication.
- SMTP authentication.
- Folder discovery.
- Message synchronization.
- Message sending.
- Draft handling.
- Flag updates.
- Folder operations.
- Attachment retrieval.
- Sending limits.
- Provider error normalization.
- Disconnection and reconnection.

For Hostinger Email, the documented configuration currently includes:

- IMAP: `imap.hostinger.com`, port `993`, SSL.
- SMTP: `smtp.hostinger.com`, port `465`, SSL.
- Alternative SMTP: port `587`, STARTTLS.

These values must be configurable rather than hardcoded.

Check the actual provider plan's sending, mailbox, connection and rate limits.

Do not assume Hostinger supports every delivery webhook or advanced email-tracking event.

## 2. Cloudflare Worker feasibility

The intended background execution environment is Cloudflare Workers Free.

Inspect the existing Wrangler configuration and runtime compatibility date.

Cloudflare Workers supports outbound TCP connections, as well as Node-compatible `net` and `tls` APIs with the appropriate compatibility configuration.

However, compatibility must be proven using the actual IMAP and SMTP libraries chosen for EIDEN Reach.

Implement a small integration proof of concept:

1. Resolve the configured server.
2. Establish the TLS connection.
3. Authenticate to a dedicated test mailbox.
4. Read a controlled test message.
5. Send a controlled test message.
6. Disconnect safely.
7. Record sanitized timing and failure information.

Never log credentials or email body content.

Cloudflare Free currently has a 10 ms CPU budget per invocation, 100,000 daily requests, 128 MB memory, five Cron Triggers per account and a maximum of six simultaneous outgoing connections per request.

Cloudflare Queues Free currently includes 10,000 operations per day and 24-hour message retention.

Design around those limits and verify them against current official documentation at implementation time.

Relevant references:

- https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/
- https://developers.cloudflare.com/workers/runtime-apis/nodejs/net/
- https://developers.cloudflare.com/workers/runtime-apis/nodejs/tls/
- https://developers.cloudflare.com/workers/platform/limits/
- https://developers.cloudflare.com/queues/platform/pricing/
- https://developers.cloudflare.com/queues/platform/limits/

Port 25 is prohibited for outbound TCP connections from Workers. Do not use it for SMTP.

If a chosen email library cannot run reliably in the Worker runtime, find a compatible implementation or document the smallest practical alternative. Do not silently move the email system to an unrelated paid provider.

## 3. Mailbox synchronization

Implement incremental IMAP synchronization.

Use mailbox folder names, UIDs and `UIDVALIDITY`, plus `MODSEQ` when supported.

Do not rely exclusively on message dates as the synchronization cursor.

Support:

- Initial folder synchronization.
- Incremental synchronization.
- New messages.
- Read/unread changes.
- Flag changes.
- Deleted or moved messages.
- Folder changes.
- Connection interruption.
- Reconnection.
- Authentication expiry.
- Duplicate prevention.
- Synchronization recovery.

Use bounded polling with short-lived connections rather than depending on a permanently connected IMAP IDLE session inside ephemeral Workers.

Define a configurable polling frequency within the actual runtime and provider limits.

Make sure folders such as Sent, Drafts, Trash and Spam are discovered from the mailbox where possible rather than assuming identical folder names across providers.

## 4. Sending and Sent-folder reconciliation

When sending via SMTP:

- Generate and preserve message identifiers where appropriate.
- Maintain the relationship between the application send record and the SMTP submission.
- Save or synchronize the sent message in the correct provider folder.
- Avoid creating duplicates when the provider automatically saves sent messages.
- Reconcile an uncertain SMTP send by checking available identifiers and sent-folder evidence.

Use correct MIME formatting and support HTML and plain-text alternatives.

Validate recipients, sender authorization, reply-to addresses, CC and BCC.

Never allow users to send from a mailbox they do not control or have permission to use.

# PART 6 — EMAIL THREADS AND REPLY DETECTION

Replies must be detected and linked to the correct CRM contacts and sequence enrollments.

## 1. Threading

Use:

- `Message-ID`
- `In-Reply-To`
- `References`
- Provider identifiers.
- Mailbox folder identifiers.
- Sender and recipient matching.

Do not group all emails with the same subject into a conversation.

Follow-up steps should preserve conversation threading where the provider supports it.

## 2. Reply processing workflow

When a new incoming message is synchronized:

1. Identify the message and mailbox.
2. Prevent duplicate ingestion.
3. Parse message headers and participants.
4. Find the matching conversation.
5. Match the sender to an existing CRM contact when reliable.
6. Save the message.
7. Add the event to the CRM activity timeline.
8. Identify relevant active sequence enrollments.
9. Pause or stop the relevant sequence enrollments.
10. Notify the assigned salesperson.
11. Create any configured CRM task.
12. Update sequence analytics.

Handle alias addresses and multiple associated mailboxes carefully.

If a message cannot be confidently matched, place it in an unmatched or needs-review state.

## 3. Reply classification

Build optional AI-assisted reply classification.

Possible categories:

- Interested.
- Wants more information.
- Meeting request.
- Pricing question.
- Objection.
- Not interested.
- Referral.
- Out of office.
- Unsubscribe.
- Automated response.
- Unknown.

Separate classification from factual message detection.

A reply from the actual prospect is a reply event. Whether it is positive or negative is an additional classification.

Do not use AI classification to override a clear unsubscribe request.

An out-of-office response should not be treated as a normal positive reply or automatically cause the system to send an immediate follow-up. It can be handled through a separate configurable pause rule.

For uncertain classification, create a review task.

## 4. Reply-based sequence stopping

By default, a human reply should stop the current outbound sequence for that contact.

Provide a carefully configured global stop option for other active sales sequences if appropriate.

Do not automatically stop unrelated transactional emails or legitimate newsletters without an explicit policy.

Make the stopping action atomic with the decision to schedule or send the next email wherever possible.

The final worker must re-check the contact and enrollment's eligibility immediately before sending.

# PART 7 — EMAIL DELIVERABILITY, BOUNCES AND UNSUBSCRIBE

Build these features from actual available provider signals.

## 1. Delivery states

Use precise statuses:

- Created.
- Queued.
- Processing.
- SMTP accepted.
- Delivery confirmed, only where actual confirmation exists.
- Temporarily bounced.
- Permanently bounced.
- Failed.
- Unknown / requires reconciliation.

Do not classify SMTP acceptance as guaranteed inbox delivery.

## 2. Bounce handling

Where available, receive and parse delivery-status notifications.

Support:

- Hard bounce.
- Soft bounce.
- Invalid recipient.
- Mailbox unavailable.
- Domain not found.
- Policy rejection.
- Sending restriction.
- Authentication failure.
- Provider error.

Classify errors conservatively.

Hard bounces should suppress the recipient from future sends as appropriate.

Soft bounces may be retried according to a configurable, bounded policy. Do not retry permanent failures.

Do not fabricate bounce events when the provider supplies no reliable event.

## 3. Spam complaints and inbox placement

The application cannot generally inspect or delete emails in an arbitrary recipient's Spam folder.

Do not build a fake feature that claims to remove messages from recipients' Spam folders.

Instead implement:

- Complaint-event ingestion when a provider supports it.
- Bounce monitoring.
- Sender health checks.
- Domain authentication checks.
- Campaign pause rules.
- Recipient suppression.
- Optional inbox-placement testing.
- Sender reputation warnings.

Keep the distinction between an actual complaint, a suspected spam placement and an ordinary sending failure.

## 4. Unsubscribe and suppression

Build a global suppression system with:

- Email address.
- Organization scope where relevant.
- Reason.
- Source.
- Event date.
- Related campaign.
- Related provider event.
- Who performed the action.

Before every send, verify suppression status.

For opt-in marketing campaigns, implement appropriate unsubscribe headers and accessible unsubscribe handling, including one-click unsubscribe where required.

Treat unsubscribes and spam complaints as high-priority events.

Do not allow a salesperson to override a global suppression record without an explicitly authorized administrative process and an appropriately lawful reason.

# PART 14 — REQUIRED ACCEPTANCE TESTS

Create automated tests for these scenarios.

1. A contact cannot be enrolled twice into a conflicting active sequence.
2. A sequence can be created, edited, saved as draft and launched.
3. Individual enrollments maintain independent progress.
4. Delay steps schedule the next step at the correct time.
5. Branch steps follow the correct conditions.
6. A human reply stops future steps according to the configured policy.
7. An out-of-office reply is not misclassified as positive engagement.
8. An unsubscribe blocks all applicable queued sends.
9. A hard bounce suppresses the recipient.
10. A temporary error can be retried safely.
11. A permanent sending error does not trigger infinite retries.
12. A worker restart does not execute the same step twice.
13. A missing queue message can be recovered from durable database state.
