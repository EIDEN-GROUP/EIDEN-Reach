# EIDEN Reach — Repository-Specific Email System Completion

You are working directly in the existing public repository:

https://github.com/EIDEN-GROUP/EIDEN-Reach

The repository has already been audited at a high level. Read the existing README, `Docs/design.md`, `Docs/implementation-plan.md`, `workers/mailbox/README.md`, the mailbox credential migration and all relevant source files before implementation.

## What already exists

The repository contains:

- React + TypeScript + Vite frontend.
- Supabase Auth and PostgreSQL database foundation.
- CRM contacts, companies, deals, tasks and activity records.
- Sequence and campaign database foundations.
- Mailbox account metadata and encrypted credential storage.
- A Cloudflare mailbox Worker that verifies IMAP and SMTP authentication.
- A durable job dispatcher.
- A read-only MCP server skeleton.
- A detailed application design system.

Do not replace these systems without demonstrating why the existing implementation is unsuitable.

## What is incomplete

The repository documentation identifies the following missing functionality:

- Incremental mailbox synchronization.
- Folder and message synchronization.
- MIME parsing and safe email rendering.
- Email threading.
- Email composition and sending.
- Reply processing.
- Sequence execution.
- Concrete background email job handlers.
- Campaign sending and delivery event processing.
- Functional prospecting and enrichment.
- Production deployment.

Your task is to complete the email system using the existing architecture.

## Phase 3 — Complete the sequence system

Build a complete sequence execution engine using the existing database and dispatcher infrastructure.

The sequence builder must support:

1. Send email.
2. Wait or delay.
3. Wait for reply.
4. Conditional branch.
5. Create CRM task.
6. Update CRM record.
7. End sequence.

Each enrollment must independently track its current step, execution state, scheduled time, retries and completion reason.

Build a visual sequence editor that supports editing, saving, duplicating, testing, pausing, resuming and activating sequences.

Before activation, show:

- Selected contacts.
- Eligible recipients.
- Excluded recipients and reasons.
- Selected mailbox.
- Sequence steps.
- Schedule and time zone.
- Sending limits.
- Missing personalization variables.
- Approval requirements.

Do not activate sequences using mock data or frontend-only timers.

## Phase 4 — Reliable execution

Use durable database jobs as the source of truth.

Implement:

- Persistent scheduling.
- Atomic job claiming.
- Idempotency.
- Concurrency protection.
- Bounded retries.
- Dead-letter handling.
- Job recovery.
- Stuck-job reconciliation.
- Sequence versioning.
- Sender rate limits.
- Final suppression checks before every send.

Do not assume Cloudflare Queues are permanent storage.

Do not retry SMTP sends blindly when the provider may have accepted the email before a connection timeout.

## Phase 5 — Reply detection and automation

When an incoming email is synchronized:

- Match it to the correct conversation.
- Match the sender to a CRM contact when reliable.
- Record the email in the CRM activity timeline.
- Detect relevant active sequence enrollments.
- Stop future automated steps according to the configured policy.
- Notify the salesperson.
- Create follow-up tasks.
- Update sequence analytics.

Support reply classifications such as interested, not interested, meeting request, objection, out of office, unsubscribe and unknown.

Treat a human reply as a factual event. AI classification is a separate interpretation.

## Phase 6 — Deliverability and safety

- Unsubscribe.

- Sender health.
- Provider error handling.
- Campaign pause rules.
- Domain authentication guidance.

Do not claim SMTP acceptance guarantees inbox delivery.

Do not claim to remove messages from recipients' spam folders.

Do not fabricate open, click, delivery or reply events.

## Phase 7 — Provider and deployment validation

The current intended stack is:

- Supabase for Auth and PostgreSQL.
- Vercel for the frontend.
- Cloudflare Workers for mailbox and background processing.
- Hostinger or another compatible provider for custom-domain mailboxes.

However, validate the runtime and provider compatibility.

The repository documents that Cloudflare Workers Free has a 10 ms CPU budget, which may be insufficient for the current mailbox TLS connection workflow.

Measure the actual connection behavior.

Do not enable production sending until the selected email provider's policies and limits have been reviewed.

Hostinger's published policy prohibits unsolicited email. Do not implement cold outreach sending through Hostinger SMTP.

Do not silently move the application to a paid provider or change the deployment architecture. Present alternatives and their costs before making such a change.
